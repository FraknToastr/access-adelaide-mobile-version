    A HELPING HAND

    help.

    Clear information. No surprises.

    Changing settings in this app does not change settings in your phone.

    A design prototype, not a live service.All point locations, facilities, routes and access descriptions are mock examples. No information has been checked by Council.

    Using this app
    • Explore: use the map or the equivalent places list. Filter by layer.
    • Journey: choose a starting point and destination, then calculate a local walking-network route. Unknown typed places must be selected on the map.
    • Access: adjust text, contrast, spacing, motion and controls.
    • Keyboard or switch: use Tab to move, Enter to activate, and Escape to close a dialog. Radio choices support arrow keys.
    • Voice control: speak a button’s visible label. Icons also have text or accessible names.
    What works without the internet?

    The ZIP bundles the app and mock data for local use. Lists, communication cards, route samples and written steps do not need online maps. MetroMap and Esri tiles need internet.

    On the hosted version, keep the loaded page open or download the ZIP before going offline. The online street basemap needs internet. This prototype does not download real maps or guarantee offline navigation.

    Accessibility design & testing

    Designed toward WCAG 2.2 AA, with selected AAA features such as larger targets, stronger text contrast and prominent focus. This is an aim, not a conformance claim or a score.

    • Semantic headings, forms, native controls and page landmarks.
    • Visible labels, error text, non-colour cues and status announcements.
    • A full list and written directions beside the visual map.
    • Spoken screens only after you choose them. No automatic advancing, flashing, location tracking or time limits.
    • Zoom enabled, text scaling, reflow, portrait and landscape support.
    • Dialog focus handling and a strong focus outline.

    Still requires testing with VoiceOver on iOS, TalkBack on Android, switch input, voice control, browser zoom, forced colours and people with varied access needs. Real route accessibility needs verified data and field testing.

    Privacy & stored information

    There is no sign-in, analytics or automatic location access. Only your chosen settings and one saved journey with endpoint coordinates can be stored locally. Browser storage can be cleared or unavailable.

    The online basemap contacts MetroMap or Esri servers, which receive network information such as your IP address. Turn off Online basemap tiles in Legend → Map options to stop new tile requests. Browser speech may use a device or network service.

    A GUIDE FOR THE NEXT VERSION

    Browser or native app?

    Which limits can we remove, which permissions would help, and what stays in the user’s hands?

    A permission unlocks access.
    It doesn’t build the feature.

    A native app can use more device services. It still needs the right code, user consent, supported hardware and operating-system approval.

    This is a planning guide, checked 27 October 2026. No permissions are requested here. Use this guide to understand which features need native development. Each feature also says what this mockup currently does.

    Understand the three kinds of app
    What each approach changes
    ApproachWhat it means
    BrowserA website in a tab. Many access features already work here.
    Installed web app (PWA)The same web technology, with a Home Screen launch and optional offline caching and notifications. It keeps browser security limits.
    Native or hybrid appAn installed app using iPhone or Android APIs. A hybrid app needs native modules; wrapping a website alone doesn’t add these capabilities.
    Compare a platform

    Choose the approach you want to understand. This does not change your phone.

    Feature group

    Three boundaries worth keeping clear

    • Inside this app: a permanently available communication button or floating dock is possible on the web. It needs design and implementation, not special device permission.
    • Outside this app: Home Screen widgets, Lock Screen information and an overlay above other apps are different features. Android and iPhone do not offer the same options.
    • Across the whole phone: there is no universal “configure accessibility” permission. Use supported settings links and guidance, and keep system-level choices with the user.
    How this should shape onboarding
    1. Ask what would help. Offer reading aloud, larger controls, communication tools, calmer screens and input choices. A diagnosis is not needed.
    2. Configure the app immediately. Text size, palette, layout, a communication shortcut and an in-app dock do not need microphone or location access.
    3. Separate speaking from listening. Read-aloud does not need a microphone. Voice commands or live transcription do, and should be optional. Audio and text choices should be independent.
    4. Offer device setup as a separate step. Explain useful system tools such as VoiceOver, TalkBack, Voice Control, Voice Access, switch input and accessibility shortcuts.
    5. Request access when it becomes useful. Explain why location, a microphone, motion or notifications are needed. Ask one relevant permission at a time. Declining must leave a useful alternative.
    6. Keep control with the person. Make speech stoppable, motion optional, gestures replaceable with buttons, and tools easy to change or turn off.

    The setup uses these principles. Native integrations described in this guide remain future work.

    What this browser exposes

    These checks only detect whether an interface exists. They do not test hardware, permission grants, reliability, accessibility or background operation. Nothing is recorded or sent.

    Sources & platform caveats

    Support varies with browser, operating-system version, installed services, hardware and organisation policy. Native implementations still need real-device tests and, where relevant, store-policy review.
